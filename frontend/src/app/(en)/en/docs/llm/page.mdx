## Where a language model is used

| Task                          | Current model                   | Fallback              | Why a model, not a rule                                  |
| ----------------------------- | ------------------------------- | --------------------- | -------------------------------------------------------- |
| Query understanding           | gpt-5.4-mini                    | gemini-3.1-flash-lite | Free-form Persian; output guarded for numbers and quotes |
| Matching judge                | gemini-3.8-flash                | gpt-5.4-mini          | Visual comparison of rooms that hashes miss              |
| Review summary                | gemini-3.8-flash, low reasoning | gpt-5.4-mini          | Summarising text with citations                          |
| "Why this villa?" explanation | gemini-3.8-flash, low reasoning | gpt-5.4-mini          | Persian prose around slots                               |
| Claim extraction (residue)    | gemini-3.1-flash-lite           | gpt-5.4-mini          | Sentences the rules could not read                       |

The "deterministic first" rule: regex, rules and pHash come first; the model sees only the residue.
gpt-5-nano was excluded on purpose: it failed the extraction probe. Text embeddings (ADR-0006) are
not built: vector retrieval does not ship until the retrieval evaluation (M8 criterion 2) shows it
is better, and image embeddings are local (DINOv2, ADR-0012).

## The call chain

  name="llm-chain"
  caption="Routing, cache, retry, budget and output validation, before the provider"
  locale="en"
/>

<Steps>
  <Step title="Routing">
    `RoutedLLMClient` tries each task's primary model and then its fallbacks, only on transport or
    availability errors, with a per-task concurrency limit. Routing sits above the cache because the
    cache key depends on the model: a fallback's reply is never served in place of the primary.
  </Step>
  <Step title="Cache">
    The key is a sha256 of the provider, model, `prompt_id@version`, messages (with image hashes),
    schema and parameters. Any prompt template change bumps the version; a test checks the template
    hashes so it is not forgotten. Every cache hit also gets a zero-dollar row in the cost ledger.
  </Step>
  <Step title="Retry">
    Exponential backoff with jitter, honouring `Retry-After`. Invalid output is asked again with the
    validation feedback. "Quota exhausted" is never retried.
  </Step>
  <Step title="Cost governor">
    Before every call, the worst-case cost is reserved and checked against the task budget and the
    project cap ($30). Every attempt, even a failed one, is a row in `ops.llm_call`.
  </Step>
  <Step title="Structured output">
    Pydantic validation with a strict json_schema. `finish_reason=length` on reasoning models is an
    error, not a partial answer.
  </Step>
</Steps>

## Estimating before running

Every LLM use case implements `plan()`, so `--dry-run` estimates the cost with no calls at all:
cache hits are subtracted, and tokens and cost come from each model's calibrated estimator and the
price list. Examples: the review summary estimate was 3% and the claim reading estimate 22% away
from the cost ledger (criterion ±25%).

```bash
make dry-run JOB=llm-smoke                                       # price a job with zero calls
cd backend && uv run villasanj er judge --low -2 --high 3 --dry-run
cd backend && uv run villasanj llm spend                         # ledger totals and the cap
```

## Tests and offline mode

- **Tests never call the real API:** `FakeLLMProvider` is deterministic and scripted. Live tests
  carry the `live_llm` marker, run only through `make test-live`, and are capped at $0.05.
- **Offline demo:** `LLM__PROVIDER=offline` answers from the cache only; a cache miss means 503,
  and the page drops or replaces that section.
- **The key:** only in `.env`; never in code, logs, error messages or commits. `.env.example` has no
  values, and gitleaks runs in pre-commit.

## Adding a provider

One adapter for `RawModelProvider`, one branch in `build_provider` and a value for
`LLM__PROVIDER`. Model names go in `config/llm.toml`. The decorators and use cases do not change.
